# Reusable master prompt — WebRAG submission showcase

> **Exact prompt requested by the project owner.** This describes the final deliverable and the order of execution. It does not replace the recorded demonstration or its verification report.

You are a senior product engineer, interface designer, full-stack reviewer, and technical demo producer. Work in the WebRAG repository at `https://github.com/9059Rohith/WebRAG-Grounded-Website-Intelligence-Agent`. The deployed app is `https://webrag-assessment.vercel.app/`. Complete the MyAdvice Website-Grounded RAG Agent assessment to a polished, truthful, submission-ready standard. Do all reasonable work end to end without asking me routine questions.

**Execute in this order:**

1. Audit the actual app, source, public deployment, evaluation records, and README. Identify rough edges that could obscure the assessment requirements. Make the application visually excellent while keeping it fast, responsive, accessible, and useful. Add only features that clarify the product, such as inspecting the answer trail, exact evidence, copyable source attribution, clear refusal, query history, token/cost disclosure, and mobile access to citations. Preserve real backend behavior; never substitute prewritten demo answers for live requests. Test desktop, phone, keyboard, reduced-motion, loading, success, refusal, error, and no-horizontal-overflow states. Deploy the finished app and verify real questions end to end.
2. Upgrade the GitHub README to an industry-standard submission page. Put a custom project cover at the start, followed by immediate live-app and video links, the problem and product outcome, real desktop/mobile screenshots, the key features and their verified states, a beautiful architecture image, a concise technical stack and repository map, setup/run instructions, evaluation results with raw evidence and honest failure notes, cost analysis at 100/1,000/10,000 queries, known limitations, and the walkthrough link. Create a full project poster image and a clear architecture image. Keep visual assets in the repository, link every claim to source or measured evidence, and push these assets **before** recording the repository portion.
3. Produce one high-quality **10–15 minute browser walkthrough**. The **first 7–8 minutes must be the actual deployed app in a browser**. Show its opening screen, 40-page/1,597-passage library, How it works panel, real question submission and processing, cited answer, inline citation focusing an exact source, original documentation URL, answer trail, usage/cost display, copying answer with sources, multi-passage comparison, correction of a misleading question, an honest unanswerable refusal with zero supporting passages, recent-question history, new conversation, motion control, and narrow mobile evidence. Do not merely show still images or describe features without working interaction. Then **open the actual published GitHub README in the browser** and tour its cover, project poster, real screenshots, architecture, evaluation, costs, setup, limitations, and links. Show the main architecture diagram clearly during the README segment. Narrate why each feature matters and tie the visual to the assessment requirement.
4. My webcam is damaged. Say that plainly at the start and near the close. Use screen video with clearly disclosed synthetic narration; do not impersonate my voice or claim webcam presence. Include understandable audio, selectable English subtitles inside the MP4, a separate `.srt`, and a full transcript. Pace narration so every important screen is legible. Use restrained camera movement, deliberate cursor actions, and clean typography. Avoid fabricated metrics, hidden failures, credentials, copyrighted stock media, or unsupported claims such as “perfect accuracy.” Preserve the difference between an independent baseline and an inspected follow-up regression.
5. Verify the final work. Build and test the app, run real hosted questions, inspect browser errors and mobile layout, confirm the GitHub assets render, decode the entire MP4, check duration/video/audio/subtitle streams, inspect representative frames from app and README sections, confirm non-silent narration, verify subtitle timing, and compare the Downloads copy with the repository artifact by hash. Push source, assets, README, prompt, plan, video, captions, transcript, and verification record to GitHub. Copy the finished MP4 and captions into my Downloads folder. Return clickable links to the deployed app, GitHub repository, walkthrough, and local Downloads files, with any remaining external blocker stated clearly.

## Execution checklist

1. **Product audit and enhancement:** real UI feature work, responsive/accessibility pass, frontend build and local/browser checks.
2. **Deploy and live QA:** publish the updated app; ask straightforward, comparison, misleading, and unanswerable questions against the public endpoint.
3. **Repository presentation:** publish the cover, poster, screenshots, architecture, evidence, README, and honest CI/evaluation caveats.
4. **Recorded app demonstration:** capture actual browser interactions for 7–8 minutes on the deployed app.
5. **Recorded repository tour:** navigate the published GitHub README and architecture in the same video.
6. **Media finishing:** align disclosed narration, subtitles, transcript, poster frame, and Downloads copy.
7. **Final verification:** inspect streams, frames, audio, citations, links, git state, and release artifact hashes.
