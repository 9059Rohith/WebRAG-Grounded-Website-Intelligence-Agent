# Security

The system ingests untrusted public HTML and serves questions against a bounded local snapshot. Its assets are the host/network, API credentials, corpus integrity, query confidentiality and query/cost availability. It is an assessment implementation, not a completed production security review.

| Threat | Implemented mitigation | Residual risk / operational action |
|---|---|---|
| SSRF / cloud metadata / DNS rebinding | HTTP(S) only, origin/path scope, userinfo and unexpected port rejection, any non-public resolved address rejected, DNS validation/pinning at connect time, redirects checked individually, environment proxy disabled | Crawler integrates with an httpcore transport implementation; upgrades require retesting. Owner-controlled allowlist and network egress policy add defense. Test-only localhost allowance must never be exposed publicly. |
| Malicious / oversized pages | robots rules, content-type and streamed size caps, bounded redirects/retries/depth/pages and sequential host delay | HTML parsers and model downloads are dependencies; pathological bounded content can still consume CPU. |
| Prompt injection | escaped delimited sources and quote table, source-only system contract, no query-time tools, strict claims, exact evidence verification, suspicious question/excerpt checks and bounded refusal | Prompt filtering is heuristic. Quoting a malicious sentence is distinct from obeying it but can still be undesirable. Recorded provider/security diagnostics do not establish universal injection resistance. |
| Fabricated citations / unsupported claims | server-owned chunk IDs/URLs and exact quote IDs, matching-reference binding and server-restored source evidence, occurrence/provenance validation, separate semantic completeness verdict | A real quote can be irrelevant to a claim. Unknown or mismatched references remain invalid; a provider verdict can still err. Exact provenance does not independently establish entailment or completeness. Human review is needed for high-stakes use. |
| Data exfiltration / secrets | no model-driven shell/files/HTTP tools; credentials use SecretStr/env, .env ignored, prompts contain bounded public corpus and the user question | The measured OpenAI path sends questions, selected public context, quote-table evidence and proposed claims to the provider for generation and verification. Consider query privacy and provider data policy; never include secrets in questions or recordings. |
| API abuse / resource exhaustion | validated bounded input, process-local sliding-window rate limit, semaphore/query timeout, optional constant-time bearer authentication, cache capacity/TTL, output/retry caps | Limits are per process and IP; proxy identity needs configuration. A timeout cannot necessarily cancel background provider/CPU work. Shared Redis quotas and billing budgets are needed for multi-worker public service. |
| Web / transport attacks | CORS closed by default, stable errors, no-store/nosniff headers, request IDs, intended HTTPS platform ingress | Owner must configure HTTPS, auth and trusted reverse proxy. A browser form is a convenience surface rather than a hardened public SaaS UI. |
| Secret leakage in logs/source/container | structured events contain safe metadata rather than questions/provider bodies, SecretStr settings, .gitignore/.dockerignore, no committed key, non-root container configuration | Tests/scans reduce risk but cannot prove no secrets. Never paste keys in CLI arguments, examples or recorded screens. |
| Stale / poisoned index or cache | persisted model identity and index version, immutable generation collections/JSON snapshots with atomic stats pointer, cache keyed by index, unique temporary embedding-cache writes, safetensors-only local weights with remote code disabled, no pickle index loading | Intentional owner ingestion can introduce malicious facts. There is no source trust ranking, contradiction resolution or automatic freshness schedule. |
| Supply chain | exact dependency locks, Ruff/mypy/Bandit/pip-audit configured, preserved CI workflow with offline fixtures | Pinning is not vulnerability immunity. The workflow is inactive under docs/ci until owner activation because publication credentials lacked workflow permission. Review actual scan/build results; prepared configuration is distinct from execution. |

Offline security tests include unsafe URL/DNS/redirect cases, malicious source/question fixtures, forged quote/source validation, auth/rate/input checks and error handling. Runtime verification status and real scan summaries belong in the final submission report; configuration files alone are not evidence that CI or Docker ran.

## Dependency audit exceptions

The saved initial `pip-audit` output (`artifacts/audit.json`) reports four distinct unpatched Chroma advisories; one is duplicated by the advisory feed. The security command explicitly ignores these IDs rather than hiding the scope exception:

| Advisory | Reported affected surface | Why this deployment does not expose that surface |
|---|---|---|
| PYSEC-2026-311 / CVE-2026-45829 | Chroma collection-creation HTTP route accepting an attacker-selected model with remote code enabled | Embedded PersistentClient only; no Chroma HTTP server, attacker-selected embedding function or `trust_remote_code=True`. |
| PYSEC-2026-3814 / CVE-2026-45833 | Chroma collection-update route accepting a remote-code model | Same boundary; model and provider names are owner configuration, not API request fields. |
| PYSEC-2026-3815 / CVE-2026-45831 | Chroma SimpleRBAC cross-tenant authorization | No exposed Chroma server/RBAC/multi-tenant deployment. The application is single-tenant. |
| PYSEC-2026-3813 / CVE-2026-45830 | Chroma server tenant/collection authorization | No exposed Chroma server or direct collection API. |

This is a deployment-specific acceptance, not a claim that Chroma is patched or vulnerability-free. Reevaluate immediately before exposing a Chroma server, dynamic models, RBAC or multiple tenants. The initial direct audit skipped the CPU-specific PyTorch wheel because its local version was not found on PyPI. The final audit wrapper normalizes the official `torch==2.14.0+cpu` wheel to its upstream `2.14.0` release for advisory checking; installation provenance is the official PyTorch CPU index. The final wrapper audit skips no runtime packages and reports no known vulnerabilities after five advisory records are ignored for the four distinct Chroma IDs above. This is advisory matching against the upstream release, not a separate binary analysis.

Deployment practice: keep API_TOKEN/OPENAI_API_KEY only in platform secrets; expose the API behind HTTPS; mount corpus/index storage with a backup; restrict crawler egress; run ingestion separately from serving; bound account spend; use shared quotas when scaling. Avoid sensitive information in user questions if enabling external synthesis. Report a suspected security defect privately to the repository owner; do not publish secrets or exploit payloads containing private data.
